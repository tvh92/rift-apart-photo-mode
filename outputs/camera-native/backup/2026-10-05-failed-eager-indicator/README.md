The Overstrike profile installs PhotoMode-10x-Tether1000.stage for the native Free camera's fixed 10x movement and 1000 tether. This separate, locally built hid.dll loads with the game and adds held-Shift 100x movement without starting the Python helper. Do not run the old helper at the same time.

Launch normally and choose Photo Mode > Free. Hold Shift while the game is focused to boost. Ctrl+Alt+F10 disables runtime boost until the next launch, restores the movement controller's captured baseline, and restores the original camera collision response. Normal, Boost, Tether, and NoClip can be edited in PhotoModeCamera.ini in the game folder; settings load at startup.

The DLL forwards all 44 exports of this machine's Windows HID library to the actual System32 DLL. Initialization starts on the first HID API call, outside DllMain. The worker verifies the exact RiftApart.exe SHA-256 before installing guarded hooks. The hooks preserve the Windows x64 calling convention, and the module is pinned for the process lifetime. The Free-camera activation hook records its entity identity; the native movement-update hook checks that identity before adjusting the live controller on the game's update thread. No heap scan or external process is required. Other camera modes and gameplay movement are not intended targets of the movement changes.

This version supports only executable SHA-256 51299faca61866cf10ea9035a15b8f22600a56557dd5ffc1aad390d5a54e6d82. A different build leaves HID forwarding active and refuses camera hooks. Another loader using hid.dll conflicts; the installer refuses to overwrite an unknown DLL. Overstrike's script cleanup targets winmm.dll rather than hid.dll. PhotoModeCamera.log in the game folder records initialization, camera matching, and speed transitions.

The source is included here. It was built using the portable official Zig 0.15.2 compiler, with the archive checksum checked against ziglang.org's download index. No third-party camera DLL was downloaded. Isolated tests verified HID GUID forwarding, export resolution, unsupported-process refusal, hook ABI preservation, owner filtering, normal/boost/release values, baseline restoration, and replacement-camera identity. The user confirmed that automatic normal and Shift speeds work in-game and continue working after leaving and re-entering Photo Mode.

Close the game before running Install-NativeBoost.ps1 or Uninstall-NativeBoost.ps1. Removing this DLL disables automatic boost; disable the .stage mod and press Install mods in Overstrike to remove the fixed camera changes. The uninstaller preserves settings and logs. Saves are not edited by these tools.

The 4 October collision update adds `NoClip=1` (also the default when the key is absent). It changes one guarded branch byte in the in-memory native `PhotomodeCameraMotionFly::UpdateMiddle` method: a collision hit no longer replaces/corrects the proposed position. The query, query cleanup, tether and remaining camera calculations stay native. This does not patch the executable on disk or a gameplay collision routine. It is a camera collision-response bypass, not a world-streaming or culling override. The user confirmed the requested wall/re-entry/speed test: "Works flawlessly, nice job."

The exact query/branch window at RVA 0x1A5F1E7 is `E8 44 AA 75 FF 84 C0 74 3B`; only the `74` at 0x1A5F1EE changes to `EB`. The DLL requires both the supported EXE hash and these original bytes, applies a byte compare/exchange, restores page protection, and flushes the instruction cache. A failed collision guard leaves the speed hooks available. Isolated tests verified the byte guard, untouched surrounding bytes, original page protection, symmetric restoration, refusal to overwrite another changed branch, and Ctrl+Alt+F10 restoration. The native function and C++ exception metadata remain in their original locations.

Geometry patch sites `0x111A860` and `0x111A9E8` have exact nine-byte instruction-window guards plus the following two-byte native AND, and aligned eight-byte compare/exchange jumps. That AND immediately overwrites flags before any consumer. Other process threads are briefly paused during installation/restoration, and a thread inside either displaced instruction window causes a retry/refusal. Relays reissue native instructions and jump back before mask/clamp handling. They preserve the original frame through registered chained unwind records; isolated checks compare the real executable's complete unwind context at every relay instruction boundary. Relays and unwind records remain alive for the process lifetime. See [Microsoft's x64 unwind documentation](https://learn.microsoft.com/en-us/cpp/build/exception-handling-x64).
