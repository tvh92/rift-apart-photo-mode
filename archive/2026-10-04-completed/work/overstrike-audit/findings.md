# Overstrike TOC, backup, and headerless movie audit

Read-only source review. No game files or process state were changed.

## Findings

1. **The install backup flow can reuse a stale `toc.BAK`, but it does not rewrite or delete it during ordinary install/uninstall.** In I29 `Prepare`, the backup is created only when absent by copying the current `toc`; then `toc.BAK` is copied back over `toc` on every prepare ([source lines 17–30](https://github.com/Tkachov/Overstrike/blob/main/Overstrike/MetaInstallers/MetaInstaller_I29.cs#L17-L30)). `Uninstall` also restores from BAK if present and does not delete it ([lines 121–133](https://github.com/Tkachov/Overstrike/blob/main/Overstrike/MetaInstallers/MetaInstaller_I29.cs#L121-L133)). With Steam-verified pristine `toc` and currently absent BAK, the next prepare should capture that pristine toc. Overstrike's source offers no explanation for an already-missing BAK; a pre-existing BAK, if stale, would override a newly verified `toc` because the copy is skipped when BAK exists.

2. **The audited Overstrike code does not write a `toc.sha1` sidecar.** The I29 sanity check computes SHA-1 of `toc` for its log ([lines 58–62](https://github.com/Tkachov/Overstrike/blob/main/Overstrike/MetaInstallers/MetaInstaller_I29.cs#L58-L62)). `Finish` calls `_toc.Save(toc)` ([lines 113–119](https://github.com/Tkachov/Overstrike/blob/main/Overstrike/MetaInstallers/MetaInstaller_I29.cs#L113-L119)); `TOC_I29.Save` opens only the requested path with `FileMode.Create` and writes the I29 magic, payload length, and DAT1 bytes ([TOC.cs lines 448–459](https://github.com/Tkachov/Overstrike/blob/main/DAT1/TOC.cs#L448-L459)). I found no `.sha1` sidecar handling in the audited flow. A public mirror of the current depot manifest lists `toc` but not `toc.sha1`; this is supporting, third-party evidence, not an official Valve file listing ([SteamDB depot 1895881](https://steamdb.info/depot/1895881/)).

3. **There is a specific case-normalization defect in the v1 `headerless` metadata parser.** `info.json` entries matching 16 hex digits are inserted verbatim into a default, case-sensitive `HashSet`; only path-based entries are converted to uppercase hex ([StageInstaller lines 129–156](https://github.com/Tkachov/Overstrike/blob/main/Overstrike/Installers/StageInstaller.cs#L129-L156)). Later, the asset key is always reconstructed as uppercase `X016` and tested with that set ([lines 161–168](https://github.com/Tkachov/Overstrike/blob/main/Overstrike/Installers/StageInstaller.cs#L161-L168)). Thus a lowercase pre-hashed `span/assetid` entry in `headerless` will fail to match. If that asset's span is divisible by 8, the fallback heuristic classifies it as having a 36-byte header; `OverwriteAsset_v1` then consumes 36 bytes before writing the asset ([InstallerBase lines 84–97](https://github.com/Tkachov/Overstrike/blob/main/Overstrike/Installers/InstallerBase.cs#L84-L97)). That would corrupt a headerless BK2. This is a concrete package-dependent bug, but it applies only if the actual NoIntro package uses lowercase pre-hashed IDs and the relevant span is divisible by 8; path entries and uppercase IDs avoid it.

4. **Stage archive assets are written consecutively without explicit padding/alignment.** `StageInstallerHelper.Work` creates a fresh `d/modN`, then passes each ZIP asset to the writer in ZIP order ([StageInstaller lines 19–34](https://github.com/Tkachov/Overstrike/blob/main/Overstrike/Installers/StageInstaller.cs#L19-L34)). `OverwriteAsset_v1` records the current stream position and copies bytes directly ([InstallerBase lines 84–97](https://github.com/Tkachov/Overstrike/blob/main/Overstrike/Installers/InstallerBase.cs#L84-L97)). The I29 DAT1 serializer does align its *TOC sections* to 16 bytes ([DAT1.cs lines 118–155](https://github.com/Tkachov/Overstrike/blob/main/DAT1/DAT1.cs#L118-L155)); that is separate from per-asset offsets inside a `d/modN` archive. The code provides no evidence that the game requires BK2 offsets to be aligned, so this is a testable hypothesis, not an identified defect.

5. **The I29 table update preserves ID-to-entry pairing.** `SortAssets` sorts a tuple of asset ID and its size/offset entry together for each span ([TOC.cs lines 608–629](https://github.com/Tkachov/Overstrike/blob/main/DAT1/TOC.cs#L608-L629)). I found no obvious sort-induced offset remapping bug in this code.

## Version/source scope

The local cached `StageInstaller.cs`, `MetaInstaller_I29.cs`, `InstallerBase.cs`, and `TOC.cs` match the corresponding blob SHA-1s in the cached current-main tree. GitHub's release page identifies OS/v1.8.1 at commit `5829f3b`, but direct fetches of that historical tag's source were unavailable in this web cache. The current-main code linked above matches the cached implementations in the relevant sections; I cannot claim an independently fetched byte-for-byte comparison against the v1.8.1 tag.

## Highest-value confirmation

Inspect the NoIntro stage package's `info.json` (read-only) and its matching BootSequence asset entry. If the headerless value is a lowercase 16-character ID, and its span is a multiple of 8, the parser defect predicts that Overstrike strips the first 36 BK2 bytes. If it is a path-based value or uppercase ID, this defect is ruled out for that clip. Compare the resulting `d/modN` asset's recorded TOC offset/size and first bytes with the package before drawing conclusions about the loading hang.
